⏺ Done. Plan written to notes/20260708-cloudflare-demo-migration-plan.md. Here's
  the thinking, and the one decision that's actually yours to make.

  The key realization

  Your server already did the hard part. It abstracts storage (local | s3, via a
  clean StorageBackend protocol) and metadata (json | postgres). That means the
  migration off AWS is almost entirely configuration:

  - Storage → Cloudflare R2. R2 speaks the S3 API, and your S3StorageBackend
  already accepts a custom endpoint_url + keys from env vars. So R2 is a
  zero-code drop-in for S3.
  - Database → delete it entirely. The json metadata backend
  (server/metadata/manager.py) stores all registry metadata as JSON objects
  inside the storage backend. With R2 storage, your metadata lives in R2. RDS 
  Postgres is fully replaced by one env var, REGISTRY_METADATA_BACKEND=json.
  Postgres only ever existed for concurrent-write/search scale you don't need
  for a demo.
  - Auth is unaffected. I checked app.py — auth state (SQLite + user/session
  files) was always on local disk, never in RDS. Kinde OIDC stays exactly as-is.

  So there are no code changes to move storage and DB to Cloudflare. That
  surprised me and it's the whole reason this is cheap and fast.

  The one real decision: where the single server runs

  The Python/FastAPI/uvicorn app cannot run on Cloudflare Workers (boto3,
  SQLite, filesystem — not a Workers-Python fit), so "single server" has to be a
  real server. Three homes, honestly ranked:

  1. Cloudflare Tunnel → the container on your Mac — $0, zero code changes, but
  only up when you start it. Best for scheduled interview demos.
  2. Tiny always-on host (Fly.io/Render/small VPS) + R2 + Tunnel — ~$0–5/mo,
  zero code changes, persistent disk, always reachable.
  3. Cloudflare Containers (native) — not recommended yet: it's beta with
  ephemeral disk, which would wipe your SQLite auth store on every sleep, so it
  needs a code change to move auth state into R2/D1 first.

  I'd default to Option 1 for interviews and graduate to Option 2 if you want
  24/7 uptime.

  Two things worth flagging

  - On "Cloudflare DB": D1 is not a drop-in — it's SQLite-over-HTTP, not
  Postgres-wire-compatible, so it'd need a new backend written. The cheapest
  supported "database" is genuinely no database (json-on-R2). I put a note in
  the plan for the future D1 path if you ever want server-side search back.
  - One risk to test first: kinnoo install hands the CLI a presigned R2 URL.
  That works, but needs REGISTRY_S3_REGION=auto and correct SigV4 — verify that
