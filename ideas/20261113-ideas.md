# kinnoo pivot ideas — 2026-11-13

**Builds on:** [20261112-ideas.md](20261112-ideas.md), which covered audit, lockfile, the policy-wrapped runner, the agent test harness, and `describe`. None of today's ideas repeats those. Idea #1 is a deliberate re-framing of kinnoo's original thesis, so it comes first.

**What changed in the field that matters for kinnoo:**
- **Packaging standards now exist, and they aren't kinnoo's.** Agent Skills (`SKILL.md`) is the shared skill format. Agent Plugins 1.0 (announced Aug 2026 by Vercel with AWS, Anysphere, GitHub, Microsoft, OpenAI) standardizes packaging around Skills + MCP. Claude Code still has its own `plugin.json` / `marketplace.json`, and Gemini/Codex/OpenCode wrappers differ. Each agent also expects skills in a different directory. Developers juggle symlinks.
- **Agent credentials are a recognized mess.** The consensus pattern is a broker that holds secrets and issues short-lived, scoped access. Agents and MCP configs shouldn't carry raw API keys. There's an IETF draft (CB4A, Mar 2026), and Enterprise-Managed Authorization is now an MCP extension. Locally, though, most people still paste keys into `mcp.json`.
- **OpenTelemetry GenAI conventions are the convergence point for tracing** (`invoke_agent` → chat → `execute_tool` spans). The conventions moved to their own repo in Jun 2026 and are not clearly stable yet. The OTel project itself recommends local, no-account viewers for dev debugging.

---

## 1. Become the package manager for *standard* formats: a cross-agent installer for Skills, MCP servers, and plugins

**Pitch:** Keep the package-manager muscle and drop the proprietary format. `kinnoo add <skill|mcp|plugin> [--to claude,codex,cursor,gemini,copilot]` installs one artifact into every agent you use. It writes each agent's own config (Claude `plugin.json`/`.claude/skills`, `.agents/skills`, Cursor/Codex MCP config, Gemini extension JSON), converts between plugin manifest flavors, and tracks what it touched so `kinnoo remove` cleans up exactly. `kinnoo sync` keeps a team's agents consistent from one checked-in file.

**Reuses:** `install_command.py` (2.3k lines of fetch → verify → place logic), `uninstall_command.py` + `install_trace.py` (the install/uninstall trace is exactly what clean multi-target removal needs), `fetch_command.py`, `sync_command.py`, `registry.py`/`registry_backends.py`/`remote_client.py` (for pulling from GitHub, skills.sh-style catalogs, or a private registry), `integrity.py` (verify on install). It pairs naturally with yesterday's `kinnoo.lock` (#2).

**Why now:** the formats are standardizing but the *installers* are per-agent, and Claude Code is outside Agent Plugins 1.0. The translation and multi-target layer is unclaimed, and it is literally what kinnoo was built to do. This time it ships other people's formats.

**First milestone:** `kinnoo add github:owner/repo/path/to/skill --to claude,codex,cursor`, plus MCP server entries into the same three. Round-trip `remove`.

## 2. `kinnoo vault`: a local credential broker for MCP servers and CLI agents

**Pitch:** Stop putting API keys in `mcp.json` and `.env`. `kinnoo vault set GITHUB_TOKEN` stores secrets in the OS keychain. MCP configs reference `kinnoo://GITHUB_TOKEN` instead of the value. When a server or agent launches through kinnoo, it gets *only* the secrets granted to it, injected at spawn time. For OAuth-backed services, kinnoo runs the browser PKCE flow once and refreshes tokens itself. `kinnoo vault migrate` finds plaintext keys in existing configs and moves them.

**Reuses:** `auth_command.py` (a full OAuth PKCE flow with a local callback server, token refresh, and revocation already exist, just pointed at the kinnoo registry today), `config.py` (auth-state persistence), `supervisor.py` (spawn-time env construction for long-running servers), `code_sweep.py` exposure patterns (to detect plaintext keys during `migrate`), `runtime_monitor.prepare_environment`.

**Why it matters:** the brokered-credential pattern is well defined for enterprise gateways (Gravitee, agentgateway, TrueFoundry), but there's no good *local, developer-laptop* equivalent. Plaintext keys in agent configs also make skills/MCP supply-chain attacks far more damaging.

**First milestone:** macOS Keychain + Linux Secret Service backends, the `kinnoo://` reference syntax in MCP configs, per-server grants, and `vault migrate` for Claude Code / Cursor configs.

## 3. `kinnoo trace`: a zero-config local OTel GenAI collector and trace viewer

**Pitch:** `kinnoo trace -- <any agent command>` sets the standard `OTEL_EXPORTER_OTLP_ENDPOINT` env vars, runs a tiny local OTLP receiver, stores spans in SQLite, and opens a local web view of the run: agent → LLM calls → tool calls, with tokens, cost, latency, and full prompts. Nothing leaves the machine. For agents that aren't instrumented, it falls back to process-level events (files touched, network calls, subprocesses) from the existing monitor, shown as spans.

**Reuses:** the Next.js `web/` app (repurposed as the trace UI; it already has layout/components/API routes), `runtime_monitor.py` events (convert violation and filesystem/network events into OTel spans), `logs_command.py` + `logging_utils.py`, `supervisor.py` stream capture.

**Why it matters:** observability is the #1 developer complaint about agents, and OTel GenAI is where instrumentation is converging. Hosted tools (Langfuse, LangSmith, Arize, etc.) need accounts and send data off-box. A `kinnoo trace --` one-liner that just works locally is a low-friction on-ramp. Exported traces also become fixtures for yesterday's test harness (#4).

**First milestone:** OTLP/HTTP receiver + SQLite + a single-run waterfall view; verify against at least two instrumented SDKs (e.g. OpenAI Agents SDK and LangGraph via OpenLLMetry/OpenInference).

**Caveat:** pin to a specific GenAI semconv version and map attribute names defensively. The spec is still moving.

## 4. `kinnoo mcp check`: a conformance and quality linter for MCP servers

**Pitch:** A quality tool for MCP server *authors*, distinct from yesterday's security audit. It starts the server (stdio or HTTP) and verifies protocol conformance: initialize handshake, capabilities, `tools/list` schema validity, error shapes, cancellation, and startup/readiness latency. Then it lints the tools: total tool-definition **token cost** (context bloat is a real problem as people stack servers), vague or duplicate descriptions, missing parameter docs, oversized enums, and names that collide with popular servers. It outputs a scorecard and a CI badge.

**Reuses:** `health_check.py` (HTTP/TCP/process checks, daemon lifecycle classification), `supervisor.py` (`ReadinessConfig`, start/stop/stream state), `validator.py` + `schema.py` patterns (structured validation with clear messages), `test_command.py` orchestration, `size_format.py`.

**Why it matters:** there are thousands of MCP servers of wildly uneven quality, and server authors have few tools beyond the MCP Inspector's manual poking. A CI-native linter with a token-budget report is concrete and immediately useful. It also gives a registry or catalog (idea #1, or yesterday's #5) an objective quality score.

**First milestone:** stdio servers only. Handshake + `tools/list` validation, token count per tool and total, a description lint, `--format json|sarif`, and a GitHub Action.

## 5. `kinnoo jobs`: a scheduler and supervisor for headless agent runs

**Pitch:** Teams increasingly run agents non-interactively: nightly dependency triage, issue labeling, report generation, using `claude -p`, `codex exec`, or custom Python agents. `kinnoo jobs add nightly-triage --cron "0 2 * * *" -- claude -p "..."` gives those runs what cron doesn't: per-job budgets (time, tokens/cost if traced), retries with backoff, concurrency limits, logs and run history, notifications on failure, and an "approval required" pause state for jobs that want a human to sign off before side effects (e.g. pushing a branch).

**Reuses:** `supervisor.py` (daemon state, pid tracking, shutdown reports), `health_check.py` (daemon lifecycle states), `logs_command.py`, `run_command.py` (process launch and I/O handling), `runtime_monitor.py` resource controls, and `web/` for a run-history dashboard. It composes with #2 (secrets per job) and #3 (traces per run).

**Why it matters:** "background agents" are a growing usage pattern, but local and self-hosted options are mostly bare cron + shell scripts, while hosted options lock you into one vendor's agent. A small, agent-agnostic job runner fills that gap.

**First milestone:** launchd/systemd-backed scheduling, a JSONL run log, retries, a timeout/budget kill, and `kinnoo jobs ls / logs / run-now`.

---

### Synthesis across both days
A consistent product shape is emerging: **kinnoo as the local control plane for the agents and tools a developer already uses.** It installs them (today #1), secures them (12th #1–#3, today #2), observes them (today #3), checks their quality (12th #4, today #4), and runs them unattended (today #5). The strongest single wedge still looks like the **installer + lockfile + audit** trio, because it reuses the most existing code and directly continues kinnoo's original distribution thesis without the format lock-in.
