## 1. Back to the origin story: **share your agent setup *and* the sessions that show how you use it**

**Pitch:** `vision.md` says kinnoo started when a friend was asked to share *"his AI coding setup and his experience (conversation history)"*. That ask is still unmet. Team setups now travel through repos (CLAUDE.md, `.claude/`, hooks, MCP configs), and Claude Code's `/team-onboarding` produces a usage-based guide. But there's no cross-agent way to **publish a whole setup plus curated, redacted session transcripts** as one browsable, installable bundle. With `kinnoo share`:
- `kinnoo share setup` captures your skills, hooks, MCP servers (as references, not secrets), rules files, and settings across Claude Code, Codex, and Cursor. Personal and memory files are excluded by default. A teammate replays it with the 13th's installer (#1).
- `kinnoo share session <id>` exports a transcript, redacts secrets, paths, emails, and hostnames, lets you trim it, and publishes it as a readable web page linked to the setup that produced it. Think "gist for agent sessions": *here's how I got Claude to do X, and here's the exact setup*.

**Reuses:** `src/kinnoo/code_sweep.py`, especially `sweep_memory_snapshot_credential_risks` and the env-var exposure sweep, which already scan agent state and memory files for credentials. That's the core of safe transcript redaction. Also `archive.py` + `pack_command.py` (bundle format), `integrity.py` / `signing.py` (tamper-evident bundles), `publish_command.py` / `fetch_command.py`, `server/routes/publish.py` + `web_agents.py` (public pages), `server/storage/s3.py`, and `web/` (transcript viewer).

**Why now:** sharing *how* you use agents is how people actually learn them. Today that happens via screenshots and blog posts, and personal files leaking into shared config is a documented failure mode. This is the one idea that fully honors the original vision without imposing a build format.

**First milestone:** Claude Code only. `kinnoo share session` → redaction preview in the terminal → a published read-only page with a "copy this setup" button.

## 2. A **context-budget MCP gateway**: per-project tool selection instead of loading everything

**Pitch:** People stack many MCP servers, and every tool definition costs context on every turn. Existing local proxies (mcpwall, mcpgate) focus on security scanning. The gap is **tool curation**. `kinnoo gateway` is a single MCP server that fronts all your others and:
- exposes only the tools allowed for the current project/profile (`.kinnoo/tools.yaml`), or exposes a small `find_tool` / `call_tool` pair that loads tools on demand
- rewrites bloated tool descriptions to shorter approved versions
- reports per-tool token cost and usage counts, so you can prune tools nobody calls
- optionally scans tool *outputs* for secrets and injection patterns (secondary)

**Reuses:** `src/kinnoo/supervisor.py` (start/stop/stream-state for multiple child server processes), `health_check.py` (child readiness), `input_guard.py` + `code_sweep.py` (output scanning, secret redaction), `size_format.py`, `logs_command.py`. It complements the 13th's `mcp check` (#4): `check` measures token cost at author time, the gateway enforces a budget at use time.

**Why it matters:** context bloat from tool definitions is a widely felt but under-tooled problem. Allow/deny lists exist in enterprise gateways, but nobody is optimizing the developer's context window locally.

**First milestone:** stdio gateway fronting N stdio servers, a per-project allowlist, a usage/token report, and `find_tool`-style lazy loading behind a flag.

## 3. **`kinnoo checkpoint`**: process-level undo for *any* agent, including shell side effects

**Pitch:** Built-in agent checkpoints (Claude Code `/rewind`, Kiro, Kilo) only track edits made through the agent's *own file tools*. Changes from shell commands, formatters, codegen, or external edits are usually not captured. Codex CLI has no production-ready undo, and people fall back to git. `kinnoo checkpoint -- <agent command>` (or as a hook) snapshots the workspace *content*, including untracked and ignored-but-relevant files, at each step. It records exactly which files changed regardless of how, and lets you `kinnoo rewind <step>` or diff any two steps. On macOS/APFS it can use copy-on-write clones to make snapshots nearly free.

**Reuses:** `src/kinnoo/runtime_monitor.py` (`_snapshot_filesystem` + `_collect_filesystem_events` already detect file changes made by an arbitrary subprocess; extend from size/mtime to content-addressed snapshots), `checksum.py` / `integrity.py` (content hashing), `diff_command.py` (`_file_change_sets` → step diffs), `install_trace.py` (JSONL trace conventions for the step log), `uninstall_command.py` (precise restore/removal patterns).

**Why it matters:** "rolling back isn't straightforward" shows up repeatedly in agent pain-point surveys. Agent-agnostic, shell-aware rollback is a clear gap and pairs naturally with the 13th's `jobs` (#5) for unattended runs.

**First milestone:** a wrapper mode with content-addressed snapshots in `.kinnoo/checkpoints/`, step diffs, `rewind`, and a Claude Code `PostToolUse` hook integration.

## 4. Refining the 12th's #4: **A/B test your agent setup**. Does this skill, MCP server, or AGENTS.md actually help?

**Pitch:** The 12th proposed a regression harness for agents. The sharper question developers keep asking is whether a given addition is *worth it*. Context files, skills, and MCP servers all add tokens, and an ETH Zurich evaluation (as reported) found repo context files often didn't improve task success while raising cost. `kinnoo ab` runs the same task suite against setup variants (with or without a skill, two AGENTS.md versions, an MCP server on or off, model A vs B) in isolated worktrees. It reports success rate, tokens, cost, wall time, and tool calls per variant, with simple significance checks so a 2-of-10 difference isn't over-read.

**Reuses:** `src/kinnoo/test_command.py` (812 lines of test orchestration), `run_command.py` (process launch and I/O), `logs_command.py`, `framework_adapters/` (tool-call capture for LangChain/LangGraph/OpenAI agents), `analyzer.py` (detect what a repo's setup consists of, to generate variants automatically). Variants can be applied with the 13th's installer (#1).

**Why it's a refinement:** the original harness answers "did my agent regress?" This answers "should my team adopt this tool or context file?", a decision people make constantly with no data. It's also a natural companion to the 14th's registry: show measured impact next to each skill or server.

**First milestone:** YAML task suite + two-variant comparison for Claude Code (`claude -p`) with per-variant token/cost from local usage logs, and a Markdown report.

## 5. **Self-hosted team usage ledger** for coding agents (the open-source middle ground)

**Pitch:** Individuals use ccusage-style local tools. Organizations buy Comet, Coralogix, Speakeasy, Braintrust, or Edgee dashboards. Small teams in between want *per-developer, per-repo, per-PR* spend and usage across Claude Code, Codex, and Cursor, without sending prompts to a vendor. A tiny `kinnoo usage push` agent on each laptop or CI runner uploads **only aggregated counts** (tokens, cost estimates, model, repo, branch; never content). A self-hosted server gives team views, budgets, and alerts.

**Reuses:** `server/` almost wholesale: `storage/tenant_store.py` + `user_store.py` (teams and members), `server/auth/*` + OIDC (SSO), `metadata/postgres_manager.py` + Alembic migrations (usage tables), `services/email_service.py` (budget alerts), plus `web/` (dashboards) and `iac/` (deploy on your AWS). Client side: `src/kinnoo/auth_command.py` (device login), `config.py`, `remote_client.py`.

**Honest positioning:** this is the most crowded space on today's list, and first-party analytics from Anthropic and others keep improving. The only defensible angles are **self-hosted + content-free + cross-agent + attribution to repo/PR**, which matters most for Codex shared workspaces, where per-person attribution is reportedly hard. It's a good fit for the existing backend, but it's a weaker standalone bet than #1–#4.

**First milestone:** a Claude Code + Codex local log parser → content-free aggregates → `POST /usage` → a per-member/per-repo weekly table in `web/`.

### Running synthesis (4 days, 20 ideas)
The ideas cluster into three lanes:
1. **Distribution & sharing of standard artifacts:** 13th #1 installer, 14th #1 private registry, today #1 setup/session sharing.
2. **Trust & safety:** 12th #1–#3, 13th #2, 14th #2/#4/#5, today #3.
3. **Measurement:** 12th #4, 13th #3/#4, today #2/#4/#5.

Lane 1 is the closest to kinnoo's original identity and reuses the most code. **Today's #1 (share setup + sessions)** is a compelling, demo-friendly front door for it: it's the thing the vision doc literally started with, and the installer and registry become its plumbing.
