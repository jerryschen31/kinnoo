## 1. **`kinnoo ci-guard`**: lint and harden GitHub workflows that run AI agents

**Pitch:** In 2026, "Comment and Control" (Johns Hopkins) and PromptPwnd (Aikido) showed that AI agents running in GitHub Actions (Claude Code Action, Gemini CLI, Copilot) can be hijacked by text in PR titles, issue bodies, or comments, and made to exfiltrate `GITHUB_TOKEN`, `ANTHROPIC_API_KEY`, cloud keys, and more, *through GitHub itself*. The root cause is structural: one job both reads attacker-controlled text and holds secrets. `kinnoo ci-guard` statically analyzes `.github/workflows/*.yml` for agent steps and flags:
- untrusted event fields (`issue.body`, `comment.body`, `pull_request.title`, `head_ref`) flowing into agent prompts
- `pull_request_target` / `issue_comment` triggers combined with secrets or a write-scoped `GITHUB_TOKEN`
- agents with unrestricted Bash / `gh` / network tools, missing tool allowlists, and missing author-association gates
- unpinned agent actions (tag instead of SHA)

`ci-guard fix` then rewrites the workflow into a **two-job pattern**: an unprivileged job that reads untrusted input and produces a structured artifact, and a privileged job with a minimal token that acts only on that artifact. It outputs SARIF for code scanning.

**Reuses:** `src/kinnoo/code_sweep.py` (secret-exposure patterns → secrets referenced in agent steps), `input_guard.py` (injection-pattern vocabulary), `validator.py` + `schema.py` (structured YAML validation with clear messages), `check_command.py` (already clones a GitHub repo and runs analysis + inspection; reuse it for `ci-guard <github-url>`), `terminal_colors.py`. Dogfood target: this repo's own `.github/workflows/` (`ci.yml`, `kinnoo-publish.yml`, `web-deploy-*.yml`).

**Why it's distinct from the 12th's `audit`:** `audit` inspects *what an agent installs* (skills, MCP servers). `ci-guard` inspects *how an agent is wired into CI*, a different, very concrete, freshly documented attack class with an obvious, mechanical fix.

**First milestone:** a rule set for `anthropics/claude-code-action`, `google-github-actions/run-gemini-cli`, and generic `claude -p` / `codex exec` run steps; SARIF output; a GitHub Action; a `fix --two-job` rewrite for the most common `issue_comment` pattern.

## 2. Refining the 12th's #5: **`kinnoo env verify`**, which makes repos bootable for *cloud* coding agents

**Pitch:** Cloud agents (Cursor Cloud Agents, Claude Code on the web and routines, Codex cloud, Copilot coding agent, Warp) all start by bootstrapping your repo in a fresh container, and that step fails a lot. Forum threads report invalid environment snapshots and failing update scripts. A Claude Code issue reports that a failed setup script was recorded as *success* and that exported env vars never reached the agent's shell. Research on LLM repo setup lists missing toolchains and dependency conflicts as recurring failures. `kinnoo env`:
- `env init` infers runtimes, versions, package managers, services, and test commands. It generates each platform's setup file from one source (`.cursor/environment.json` / Dockerfile, Copilot `copilot-setup-steps.yml`, a Claude/Codex setup script with `set -euo pipefail`).
- `env verify` runs that bootstrap **locally in a clean container**, then asserts that toolchains resolve, tests can run, and expected env vars are visible to a *fresh* shell. It fails loudly with a diagnosis before you burn a cloud agent run on it.

**Reuses:** `src/kinnoo/analyzer.py` (`_detect_runtime`, `_detect_python_version_from_pyproject`, `_detect_node_runtime_version`, `_detect_dependencies`, `_detect_node_package_manager`, `_detect_runtime_port_hint`), `runtime_language.py`, `check_command.py` (clone → analyze → preflight pipeline), `run_command.run_preflight`, `health_check.py` (service readiness), `templates.py` + `init_command.py` (file generation), the repo's `Dockerfile` / `docker-compose.yml` as reference patterns.

**Why it's a refinement:** the 12th's `describe` mentioned emitting a devcontainer as one of many outputs. This narrows it to the sharpest, most reported pain, *cloud agent bootstrap*, and adds the missing piece: **local verification** before the cloud run.

**First milestone:** Python + Node repos; generate Copilot + Cursor + generic setup scripts; `env verify` in Docker with a per-check pass/fail report.

## 3. **`kinnoo memory`**: inspect, diff, and quarantine agents' persistent memory

**Pitch:** Agents now keep long-term memory in files and stores (Claude Code memory and `CLAUDE.md` files, OpenClaw workspace memory, Cursor/Codex memories, framework memory stores). That memory is a new persistence layer for attacks: Cisco reportedly hijacked Claude Code's memory, and Forcepoint describes *persistent memory poisoning*, where an injected "fact" outlives the session and steers future ones. Meanwhile, nobody can easily see what their agents remember. `kinnoo memory`:
- `ls` / `show`: an inventory of every memory location across installed agents, with sizes and last-modified times
- `scan`: flags secrets, instruction-like content ("always run…", "ignore previous…"), URLs and exfil patterns, and entries contradicting repo config
- `diff` / `watch`: hash-baselines memory and reports what changed since the last session, and which tool or session wrote it (via a hook). It can **quarantine** new entries for human confirmation
- `prune`: expire stale entries; `export`: a portable, redacted memory bundle (pairs with the 15th's #1 sharing)

**Reuses:** `src/kinnoo/code_sweep.py` (`sweep_memory_snapshot_credential_risks` already scans "state snapshot candidates" for credentials, which is exactly this, generalized), `input_guard.py` (instruction/injection patterns), `openclaw_preflight.py` + `analyzer.py`'s OpenClaw workspace detection (`_detect_openclaw_weighted_signals`) for locating OpenClaw memory, `checksum.py` / `integrity.py` (baselines), `diff_command.py` (`_file_change_sets`), `install_trace.py` (JSONL event log conventions).

**Why it matters:** memory is becoming the stickiest attack surface *and* the least visible part of agent state. A simple, local, cross-agent inspector is cheap to build from existing code and has no clear incumbent.

**First milestone:** Claude Code + OpenClaw memory locations; `ls`, `scan`, and `diff` with a hash baseline in `.kinnoo/memory-baseline.json`; a Claude Code hook that warns when a session writes memory containing instruction-like text.

## 4. Refining the 13th's #5: **event-triggered agent runs on your AWS, with secret-separated phases**

**Pitch:** The 13th's `jobs` was a *local cron* for headless agents. The bigger production need is **event-triggered** runs: a GitHub issue labeled `agent`, a Slack request, an S3 upload, a failed deploy. Today that means GitHub Actions (with the risks in #1) or a vendor's hosted agent. kinnoo's backend already has a working *S3 event → Lambda* pipeline. Generalize it into a small "agent trigger" service:
- `POST /triggers/{name}` webhook endpoints (GitHub, Slack, generic HMAC) → queue → an ephemeral Fargate task or Lambda runs the agent CLI of your choice
- built-in **two-phase isolation**, the server-side version of #1's fix: phase 1 reads untrusted event content with *no* secrets and emits a structured plan; phase 2 runs with a narrowly scoped token and acts only on the plan
- per-trigger budgets, timeouts, logs, and optional approval (the 14th's #4) before phase 2

**Reuses:** `lambda_handler.py` + `Dockerfile.lambda` (event-parsing and run entrypoint pattern), `server/services/security_check.py` (`invoke_security_check_lambda_async` is already an async "kick off isolated work" call), `iac/modules/lambda-security-check` (S3-event → Lambda wiring + permissions), `iac/modules/ecs-fargate`, `secrets`, `iam`, `server/middleware.py` + `server/auth/token.py` (webhook authentication), `server/routes/` (new trigger routes), `web/` (run history).

**Why it's a refinement:** same "unattended agent runs" need as `jobs`, but moved to where teams actually want it (cloud, event-driven, multi-user) and built around the isolation lesson from this year's CI attacks.

**First milestone:** GitHub `issues.labeled` webhook → Fargate task running `claude -p` in phase 1 (read-only, no secrets) → JSON plan → phase 2 with a fine-grained token that can only comment or open a PR.

## 5. **`kinnoo port`**: framework-migration planner with behavior-parity checks

**Pitch:** Teams keep switching agent frameworks. One widely shared 2026 post describes a "quiet exodus" from LangChain toward vendor SDKs (OpenAI Agents SDK, Claude Agent SDK, Google ADK, Strands). OpenAI and Anthropic both publish migration cookbooks *from each other's SDKs*, and LangChain answered with Deep Agents. Migrations are mostly manual and risky because nothing checks that behavior survived. `kinnoo port` doesn't rewrite your code blindly. It:
1. **inventories** the agent in a framework-neutral form: tools (names, schemas), prompts and instructions, handoffs and sub-agents, memory and checkpointing, model settings
2. emits a **migration plan** mapping each element to the target SDK's primitive (using the vendors' own mapping tables), with "no equivalent" warnings. The plan doubles as a precise brief for a coding agent to execute
3. runs **parity tests**: the same scenarios against old and new implementations, comparing tool-call sequences and outputs

**Reuses:** `src/kinnoo/framework_adapters/` (`langchain_adapter.py`, `langgraph_adapter.py`, `openai_adapter.py` already parse these frameworks' projects), `analyzer.py` (`_detect_framework`, `_detect_langgraph_compile_signal`, entrypoint detection), `import_command.py` (GitHub/local intake), `test_command.py` + `run_command.py` for parity runs. Parity testing is a specialization of the 15th's A/B harness (#4).

**Honest caveat:** coding agents can already do much of the code rewriting, so the defensible value is the **neutral inventory + mapping + parity verification**, not codegen. Scope it as "make a coding agent's framework migration safe and checkable."

**First milestone:** LangChain/LangGraph → OpenAI Agents SDK and → Claude Agent SDK inventories for tool-calling agents; a Markdown plan; a parity run comparing tool-call traces on a 10-scenario suite.

### Running synthesis (5 days, 25 ideas)
A pattern is now clear: kinnoo's most reusable asset isn't the manifest. It's the **"understand an arbitrary agent project or environment"** machinery (`analyzer.py`, adapters, `code_sweep.py`, `check_command.py`), plus the **"run and observe something untrusted"** machinery (`runtime_monitor.py`, `supervisor.py`, the Lambda pipeline). Today's ideas are all thin products on those two cores. If you want a single quick, high-signal experiment this week, **#1 `ci-guard`** is the best one: a narrow scope, a freshly publicized attack class, an obvious fix, easy to demo on real public repos, and it mostly reuses existing scanning code.
