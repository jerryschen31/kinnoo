## 1. Refining the 12th's #2 and #3: **`kinnoo scope`**: learn a least-privilege profile by watching a run, then flag privilege drift on upgrade

**Pitch:** The 12th's policy-wrapped runner *enforces* a policy, but nobody wants to write one. The lockfile pins *bytes*, but a "harmless" upgrade that starts calling a new host or reading `~/.aws` keeps the same shape. OWASP's MCP Top 10 calls this scope creep (MCP02). `kinnoo scope` closes the loop:
- **learn:** `kinnoo scope learn -- <agent or MCP server command>` runs the target under the monitor and records what it actually touched: hosts, file paths read and written, child processes, the env vars it read, and the MCP tools called.
- **emit:** turns that record into *each tool's own* config, not a kinnoo format: Claude Code `permissions.allow/deny`, a Docker Sandboxes / devcontainer network allowlist, a macOS `sandbox-exec` / Linux bubblewrap profile, and a scoped OAuth scope list for the MCP server.
- **drift:** on the next version, `kinnoo scope diff` re-learns the profile and reports anything new ("v1.4 now connects to `telemetry.example.io` and reads `~/.ssh/config`") as a CI failure or an install-time prompt.
- **exposure preflight:** before learning, it lists what the process *could* reach (exported cloud keys, `~/.aws`, `~/.ssh`, `~/.kube`, `.npmrc`), so the emitted profile denies all of it by default.

**Reuses:** `src/kinnoo/runtime_monitor.py`. The monitor class's `prepare_environment`, `_snapshot_filesystem`, `_collect_filesystem_events`, `_collect_network_events`, and the sitecustomize socket hook (`_build_sitecustomize_source` → `_create_connection_with_monitor`) are already the "learn" step for Python processes. Also `sandbox.py` (`evaluate_sandbox_permissions`, `_iter_attempted_capabilities`) for the permission vocabulary, `code_sweep.sweep_env_var_exposure` for the exposure preflight, `diff_command.py` (`_file_change_sets`, `_manifest_change_lines`) for the drift report, and `install_trace.py` for the JSONL record format.

**Why it matters:** microVM sandboxes (Docker Sandboxes, Vercel Sandbox) are becoming the default isolation for coding agents, and Vercel itself says credential and permission scoping matters as much as the VM boundary. Sandboxes give you the *mechanism*, but nobody gives you the *policy*. An academic MCP access-control study found 80.9% of auto-generated permission manifests needed no changes, which suggests learning a policy from behavior is viable.

**First milestone:** learn mode for Python-based MCP servers (where the socket hook already works), plus output as Claude Code permissions and a network allowlist, plus `scope diff` between two versions as a GitHub Action.

## 2. **`kinnoo pr-screen`**: sandboxed proof-of-work screening for inbound pull requests

**Pitch:** Maintainers are drowning in AI-generated PRs. A Linux Foundation survey found close to a third of incoming changes on larger projects are low quality or AI-generated. Ghostty restricted AI contributions, tldraw auto-closes external PRs, curl ended its bug bounty, and GitHub has considered a PR "kill switch." The New Stack's diagnosis is that AI *review* made triage faster, but everything downstream stayed slow. Nobody runs the PR before a human looks at it. `kinnoo pr-screen` is a self-hosted GitHub App that, for each external PR:
- checks out the PR in an isolated, network-restricted container and runs the project's declared build, test, and lint commands (no secrets, no write token)
- checks basic substance: did the tests it added actually fail before the change and pass after? Does it touch sensitive paths (`.github/workflows`, auth, release scripts)? Does it add dependencies, and are they real and older than N days? Does it duplicate an open PR?
- posts a single structured "screen" comment with a label (`screen:passed`, `screen:failed-build`, `screen:needs-maintainer`), so maintainers can sort their queue by evidence rather than by vibes
- optionally reads Agent Trace data (the 17th's #2) when present, but **doesn't** try to "detect AI." The screen is the same for humans and agents.

**Reuses:** `src/kinnoo/check_command.py` (`check_target`: clone → analyze → inspect → preflight is already a "screen this repo" pipeline), `run_command.run_preflight` and `_check_preflight_dependencies`, `analyzer._detect_runtime` / `_detect_framework` / `_detect_dependencies` (to infer the build and test commands when the project hasn't declared them), `install_command._detect_node_lifecycle_scripts` and `_run_node_audit_summary` (flag new install scripts and vulnerable deps), `code_sweep.py`, and the scan-on-event backend: `server/services/security_check.invoke_security_check_lambda_async` + `iac/modules/lambda-security-check` + `iac/modules/ecs-fargate` (run screens as Fargate tasks on the maintainer's AWS).

**How it differs from the 16th's `ci-guard`:** `ci-guard` hardens workflows that *run agents*. This treats every inbound PR as untrusted input and makes it prove it builds before it costs a human anything.

**First milestone:** a GitHub App plus one Fargate task definition: Python and Node repos, build/test/lint in a container with no network, a sensitive-path check, and one labeled comment. Pilot it on a few mid-size OSS repos.

## 3. **`kinnoo skill-env`**: reproducible, sandboxed runtimes for the scripts inside Agent Skills

**Pitch:** Agent Skills can bundle scripts, but the spec has no real dependency story. The official docs point to PEP 723 inline metadata. In practice, agents discover missing packages mid-task, `pip install` ad hoc (burning tokens and installing whatever name they guessed), and results differ across machines. SafeDep's skill threat model lists hallucinated-package injection and unpinned, attacker-controlled deferred dependencies as top risks. `kinnoo skill-env`:
- reads each skill's scripts: PEP 723 blocks for Python, `package.json` or imports for Node, and inferred imports as a fallback
- resolves and **locks** them with hashes into a per-skill environment (uv / npm with `--ignore-scripts`), created at install time, not mid-task
- adds a tiny shim so the agent's `python scripts/foo.py` transparently runs in that skill's env, with network off by default at run time
- re-checks the lock when the skill updates, and pairs with #1 for the skill's file and network scope

It ships *no new format*. It reads PEP 723 and `SKILL.md` as they are.

**Reuses:** `src/kinnoo/analyzer.py` (`_infer_requirements`, `_collect_requirements_dependencies`, `_collect_pyproject_dependencies`, `_collect_package_json_dependencies`, `_detect_dependencies`), `run_command.py` (`_extract_dependency_names`, `_resolve_venv_pip`, `_check_preflight_dependencies`: venv resolution and preflight already exist), `install_command.py` (`_read_requirements`, `_resolve_node_package_manager`, `_detect_node_lifecycle_scripts`, `_install_node_dependencies`, `_install_openclaw_skill_dependencies`: kinnoo already installs skill dependencies for OpenClaw), `runtime_language.py`, `integrity.py` / `checksum.py` (hash-locking), `sandbox.py` (run-time restrictions).

**Why it matters:** skills are the fastest-growing artifact type in the agent ecosystem, and "the script needs a package" is where they break and where supply-chain risk enters. This is narrow, unglamorous, and exactly the dependency-installation work kinnoo already does, now applied to someone else's format. It's also a natural feature of the 13th's cross-agent installer (#1).

**First milestone:** Python only. PEP 723 → `uv`-locked per-skill venv under `.kinnoo/skill-envs/<skill>/`, plus a `PreToolUse` shim for Claude Code that reroutes `python <skill>/scripts/*.py` into it.

## 4. **`kinnoo ax`**: run real agents against your CLI or API and show where they get stuck

**Pitch:** "Agent experience" (AX) is now a design goal for devtool vendors. Checkly reports about half its CLI users are coding agents, and Speakeasy and Algolia rewrote their CLIs for agents. Static checklists already exist: CLI Agent Spec has 155 requirements and an audit skill, and agent-friendly-cli is a ClawHub skill. The missing piece is **empirical measurement**: give real agents (Claude Code, Codex, an OpenAI Agents SDK loop) a set of tasks that need your CLI or API, run each one N times, and report:
- task success rate, turns, tokens, and time per task, per agent
- *where* they struggled: repeated `--help` calls, hung interactive prompts, retries after unparseable output, guessed flags that don't exist, destructive commands attempted
- a before/after comparison when you change help text, add `--json`, or publish a skill or AGENTS.md for your tool

**Reuses:** `src/kinnoo/test_command.py` (`load_kinnoo_test_cases`, `run_test_command`, `validate_kinnoo_tests_document`, declarative assertions: the task-suite format), `run_command.py` (process launch), `supervisor.py` (`start_server`, `stream_output`, `wait_until_ready`, `shutdown_server_with_report` for the CLI or local API under test), `framework_adapters/` (`langchain_adapter`, `langgraph_adapter`, `openai_adapter` for tool-call capture), `runtime_monitor.py` (process and network events to spot hung prompts and wasted calls). The variant comparison is the 15th's #4 A/B harness pointed at a different customer.

**How it differs from the 15th's #4:** that one asks "does this skill help *my* agent?" for agent *users*. This one asks "can agents use *my product*?" for devtool and API *vendors*, a customer who will pay for the answer.

**First milestone:** a YAML task suite for one CLI; Claude Code (`claude -p`) and Codex (`codex exec`) as drivers, each task run 5×, and a Markdown report of success rate plus a list of where they got stuck. Dogfood it on kinnoo's own CLI first.

## 5. Refining the 15th's #5: from usage ledger to **agent-config inventory**. Which MCP servers, skills, and hooks are installed across the team?

**Pitch:** The 15th's ledger counted *usage*. The question security and platform leads actually ask first is *what's installed*: which MCP servers, versions, and launch commands; which skills and plugins; which hooks run arbitrary shell; which configs hold plaintext keys, across Claude Code, Codex, Cursor, and Gemini on every developer laptop and CI runner. This is "shadow MCP," and today it's answered by asking around in Slack. `kinnoo inventory push` collects **config metadata only** (names, versions, hashes, launch commands with secrets stripped, risk flags; never prompts or file contents). A self-hosted server then shows:
- the team-wide list of installed servers, skills, and hooks, with counts and versions
- risk flags: a plaintext key in an MCP config, an unpinned `npx` server, a hook that pipes to a shell, a server not on the team allowlist
- "who still has the vulnerable version" when an MCP server or skill advisory drops
- combined with the lockfile (12th #2) and `scope` (today #1), the allowlist becomes enforceable rather than a wiki page

**Reuses:** `server/` almost wholesale: `server/storage/tenant_store.py` and `user_store.py` (teams and members), `server/auth/` (SSO), `server/metadata/` + `server/database/` (inventory tables), `server/services/email_service.py` (advisory alerts), `web/` (dashboards), `iac/` (deploy on your AWS). Client side: `src/kinnoo/analyzer.py` detectors (`_detect_runtime`, `_detect_framework`, `_detect_dependencies`) and `code_sweep.py` (`sweep_env_var_exposure`, `sweep_asset_credential_risks`) for risk flags, `checksum.py` for hashes, and `auth_command.py` + `remote_client.py` for device login and upload.

**Honest positioning:** enterprise vendors (MCP gateways, AI-SPM products) are moving here, and Anthropic/OpenAI admin consoles may add partial views for their own agents. The defensible angle is the same as the 15th's: **cross-agent, self-hosted, content-free**. It replaces the ledger as the better use of the backend: inventory is a prerequisite for security, while spend is a nice-to-have. As before, it's more of a team-tier feature than a standalone bet.

**First milestone:** a Claude Code + Cursor config reader → metadata JSON → `POST /inventory` → a team table of MCP servers by name, version, and count, with a "plaintext key" flag.

### Week-one synthesis (7 days, 35 ideas)

The ideas keep converging on one product shape: **kinnoo as the trust and verification layer for agent tooling it doesn't own**. That means verify what you install (12th #1–#2, 17th #5, today #3), constrain what it does (12th #3, 13th #2, today #1), and prove what happened (13th #3, 17th #2, today #2). Given the July note about deferring to AgentRegistry, the strongest standalone candidates are the ones that need **no registry and no hosted service**:

1. **Today's #1 `scope`.** It's the most direct reuse of `runtime_monitor` + `sandbox`, the most distinctive, and it upgrades two earlier ideas.
2. **17th #1, Web Bot Auth.** A new standard, little tooling for independent developers, and the crypto in `signing.py` is already written.
3. **16th #1 `ci-guard`.** Concrete, attack-driven, and cheap to ship.

Today's #2 (`pr-screen`) is the best use of the existing **server + iac + Lambda** investment if you want to keep the backend alive. It targets a loud, current pain with a clear user (maintainers) and doesn't depend on any agent vendor.
