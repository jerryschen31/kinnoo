# kinnoo pivot ideas — 2026-11-12

**Constraint driving the pivot:** stop requiring developers to adopt a kinnoo-specific agent format. Each idea below works *on top of* whatever agents, skills, and MCP servers people already have. kinnoo describes and protects them; it does not prescribe how they are built.

**What the field is saying right now (Nov 2026):**
- The agent supply chain is an active attack surface. Audits of public skill registries found malicious skills at high rates, roughly 7–12% depending on the snapshot. Unpinned `npx @server/latest` installs of MCP servers are a known risk, and static scanning alone is being shown to be evadable.
- Sandboxing coding agents has become basic hygiene. New OSS entrants (Nono, Strands Box, Safehouse) show demand, but tools are fragmented by OS and none is a standard yet.
- The top developer complaints remain observability/debugging, evaluation gaps, and cost blowups, with agents that work in staging often breaking in production.

**What kinnoo already has that is format-agnostic at heart:** `analyzer.py` (~2.4k lines of project inference), `code_sweep.py` (secret/exposure patterns), `integrity.py` + `checksum.py` + `signing.py` (per-file hashes, signatures), `inspect_command.py` / `diff_command.py`, `input_guard.py` (SQLi/shell/path-traversal/SSRF detection), `runtime_monitor.py` (filesystem snapshot diffing + Python socket hooks, violation events), `sandbox.py` (permission evaluation from manifest), `supervisor.py` (daemon lifecycle), `health_check.py`, `install_trace.py`, `test_command.py`, framework adapters, the registry backend, and the Next.js web app.

---

## 1. `kinnoo audit` — a supply-chain scanner for skills, MCP servers, and agent repos

**Pitch:** Point it at anything: a `SKILL.md` folder, an `mcp.json` / `claude_desktop_config.json`, a GitHub URL, or a local agent repo. You get a risk report (CLI table, JSON, and SARIF for GitHub Code Scanning). No manifest required.

**Checks:** secrets and exfil patterns, shell-out and network calls, obfuscated or binary payloads, instructions in skill/tool descriptions that don't match the code (prompt-injection-in-metadata), unpinned dependencies (`npx pkg@latest`, `uvx` without a version), and post-install scripts.

**Reuses:** `code_sweep.py`, `input_guard.py` patterns, `analyzer.py` (to find entrypoints and dependencies in arbitrary repos), `inspect_command.py` output formatting, `import_command.py`'s GitHub clone path.

**Why it beats the status quo:** existing scanners are mostly vendor-hosted (Snyk) or single-ecosystem (OpenClaw-only vetters). A local, offline, Apache-2.0 CLI that covers *skills + MCP + agent code* in one pass, and runs as a GitHub Action, is a gap.

**First milestone:** `kinnoo audit ./some-skill --format sarif` plus a GitHub Action wrapper. Seed the rules by running `code_sweep` over the top 100 public skills/MCP servers and publishing the findings as a blog post for traction.

## 2. `kinnoo.lock` for agent tooling — pin, hash, and detect "rug pulls"

**Pitch:** A lockfile for the *tools an agent uses*, not the agent itself. `kinnoo lock` reads an existing MCP config or skills directory, resolves each server/skill to an exact version + content hash, and records the tool names and descriptions it exposes. `kinnoo verify` (in CI or at session start) fails if anything drifted: a new version, changed file hashes, or a tool description that silently changed (the MCP "rug pull" attack).

**Reuses:** `integrity.py` (per-file hash manifest is almost exactly this), `checksum.py`, `signing.py` (optionally sign the lockfile), `diff_command.py` (human-readable drift reports), `sync_command.py`.

**Why it matters:** pinning and re-verification are what static registry scanning misses. Most teams copy MCP configs between machines with no reproducibility guarantee at all. It's the `package-lock.json` moment for agent tooling.

**First milestone:** support Claude Code / Claude Desktop / Cursor MCP config formats plus `SKILL.md` directories. `kinnoo verify` exits non-zero on drift.

## 3. `kinnoo run -- <any command>` — a policy-wrapped runner for *any* agent or MCP server

**Pitch:** Drop the requirement that the agent be a kinnoo package. `kinnoo run --policy policy.yaml -- npx some-mcp-server` (or `-- claude`, `-- python my_agent.py`) applies filesystem/network/env-var policy, resource limits, a cost/time budget, and writes an audit log of what the process touched.

**Reuses:** `sandbox.py` permission model (lift it out of the manifest into a standalone policy file), `runtime_monitor.py` (violation events, resource controls, dry-run prediction), `supervisor.py` (daemon lifecycle for long-running MCP servers), `health_check.py`, `install_trace.py`.

**Honest caveat:** today's monitor detects (snapshot diffs, Python socket hooks); it does not enforce at the OS level. To be credible, this needs real backends: `sandbox-exec`/Seatbelt on macOS, Landlock + seccomp (or bubblewrap) on Linux, with the existing monitor as the cross-platform fallback. Position it as a *policy layer + audit log* that delegates to OS isolation, not as yet another sandbox. Nono/Safehouse/Strands Box are the competition, so differentiation is policy portability across OSes and auto-generating the policy from idea #1's audit ("this server only needs network to api.github.com").

**First milestone:** macOS Seatbelt backend + JSONL audit log, wrapping a stdio MCP server.

## 4. `kinnoo test` → a framework-agnostic agent regression harness ("pytest for agent CLIs")

**Pitch:** Teams have no cheap way to catch an agent regression when they change a prompt, model, or tool. Define scenarios in YAML (input, expected tool calls or output assertions, LLM-judge rubric, max cost/latency), then run them against *any* executable agent with `kinnoo test scenarios/`. It outputs pass/fail, cost, latency, and a diff against the last baseline. Ship it as a GitHub Action that comments on PRs.

**Reuses:** `test_command.py` (812 lines of test orchestration), `run_command.py` I/O contract handling (string/JSON input → parseable output was always the CLI-runnable assumption, and it fits evals perfectly), framework adapters (to hook tool-call traces where possible), `logs_command.py`.

**Why it matters:** "evaluation gaps" and "works in staging, breaks in prod" are top-cited pain points. Hosted eval platforms exist, but a local-first, CI-native, framework-agnostic runner with record/replay of tool calls (for deterministic, cheap reruns) is still underserved.

**First milestone:** YAML scenario format, exact/regex/JSON-schema/LLM-judge assertions, a `--baseline` diff, and a GitHub Action.

## 5. `kinnoo describe` — turn the analyzer into an "agent card" generator (describe, don't prescribe)

**Pitch:** Invert `kinnoo import`. Instead of forcing a repo into `kinnoo.yaml`, *read* any agent repo and emit standard descriptors the ecosystem already uses: an A2A Agent Card, an `AGENTS.md`, an MCP server manifest / registry `server.json`, a devcontainer, and a declared-permissions summary. This becomes the "README + SBOM" for agents, and other tools (including ideas #1–#3) consume it.

**Reuses:** `analyzer.py` almost entirely (entrypoint detection, deps, framework detection, confidence scores), `import_command.py` prompt/confirm flow, `schema.py` validation patterns, `templates.py`. The May 2026 import gap analysis (`notes/20260529-kinnoo-import-gaps.md` in the old kinnoo-project repo) already lists the detector work (Node/Go/framework breadth) that would make this good.

**Why it matters:** this keeps kinnoo's most expensive asset, the analyzer, while removing the format lock-in. It also gives the web app (`web/`) a natural new role as a browsable index of *described* agents/MCP servers with audit scores. That's a registry people don't have to repackage for.

**First milestone:** `kinnoo describe <repo|url> --emit agent-card,agents-md` with confidence annotations, tested against ~20 popular open-source agent repos.

---

### How these fit together
Ideas #1, #2, #3, and #5 compose into a coherent repositioning: **"kinnoo: trust tooling for the agent supply chain. Describe, audit, pin, and run any agent, skill, or MCP server safely."** Idea #4 is a standalone wedge if you'd rather go after evals. My suggested order: #1 → #2 (fast to ship, mostly existing code, clear demand), then #3 or #5.
