## 1. **Web Bot Auth for agent builders**: sign your agent's HTTP requests, host your key directory, verify others'

**Pitch:** Websites increasingly block or throttle automated traffic, and IP/user-agent allowlists don't work for agents. The IETF **Web Bot Auth** working group (chartered early 2026; `draft-ietf-webbotauth-httpsig-protocol`, Sep–Oct 2026 drafts) standardizes agents signing requests with **HTTP Message Signatures (RFC 9421)** using Ed25519 keys published at `/.well-known/http-message-signatures-directory`. Cloudflare activated verification at its edge, AWS WAF announced support, and Google is experimenting. Big operators will implement this themselves. **Independent agent developers have no easy path.** `kinnoo botauth` provides:
- `keygen` / `rotate`: Ed25519 keys, a JWK thumbprint `keyid`, and an overlapping-validity rotation schedule
- `directory serve` (or a static export for any host / Cloudflare Pages): a correctly formatted, signed key directory
- `sign`: drop-in signers for Python `httpx`/`requests` and Node `fetch`, plus a local forward proxy that signs *any* agent's outbound requests without code changes (`kinnoo botauth proxy -- <agent cmd>`)
- `verify`: FastAPI and Next.js middleware for site owners who want to recognize signed agents themselves

**Reuses:** `src/kinnoo/signing.py` (already uses Ed25519: `generate_ed25519_keypair`, `public_key_fingerprint`, `sign_payload`, `verify_signature`, PEM loading), `server/` (FastAPI app and `server/middleware.py` as the verifier reference and hosted key directory), `web/` (Next.js for the TypeScript verifier + directory pages), `iac/modules/cloudflare` (serving the well-known directory at the edge), `config.py` (key-path configuration).

**Why it matters:** as signed traffic becomes the way sites tell good agents from scrapers, unsigned agents will get more CAPTCHAs and blocks. The standard is fresh, the crypto is already in kinnoo, and the tooling for *small* agent operators is thin.

**First milestone:** keygen + a static directory export + a Python `httpx` signer + a verification round-trip test against the draft's test vectors. Then the signing proxy.

## 2. **Agent Trace for every agent**: agent-agnostic capture, signing, and review policy for AI-written code

**Pitch:** Cursor's **Agent Trace** (open RFC v0.1.0, Jan 2026; on the Thoughtworks Radar as "Assess") defines how to record which lines were written by AI vs. humans, with the model and conversation, at file/line granularity, across Git, Mercurial, and Jujutsu. Early adopters include Cline, OpenCode, and Git AI. Gaps remain: tooling is incomplete, many agents don't emit traces, and nothing *uses* them in review. `kinnoo provenance`:
- **captures** Agent Trace records for agents that don't emit them, via hooks (Claude Code `PostToolUse`) or process-level file-change capture around any CLI agent (`kinnoo provenance -- codex exec ...`)
- **signs** trace records so they're tamper-evident when they travel with a PR
- **reports** in PRs: % AI-authored by file, which sessions and models, with links to the transcript (pairs with the 15th's #1 session sharing)
- **enforces** simple review policy, e.g. "AI-authored lines under `iac/` or `server/auth/` need a second human reviewer," as a CI check

**Reuses:** `src/kinnoo/runtime_monitor.py` (`_snapshot_filesystem` / `_collect_filesystem_events` detect files changed by an arbitrary subprocess, the fallback capture path), `signing.py` (`create_detached_signature_artifacts` / `verify_detached_signature_artifacts` for signed trace records), `checksum.py` / `integrity.py` (content hashes per range), `install_trace.py` (JSONL record conventions), `diff_command.py` (`_file_change_sets`), and `check_command.py` (CI entry point).

**Why it's distinct:** the 15th's #3 `checkpoint` is about *undo*. This is about *attribution and review*, and it produces a standard format other tools read. Compliance teams and reviewers increasingly ask "how much of this PR did an agent write, and from what prompt?"

**First milestone:** Claude Code hook → Agent Trace JSON per commit (Git notes or a sidecar file), a PR summary comment, and one path-based policy check.

## 3. **`kinnoo redteam`**: canary-based injection testing that watches what the agent *does*, not just what it says

**Pitch:** Existing agent red-team tools mostly check for canary leakage in the **model's response** (AgentSeal, AgentGuardian, garak, promptfoo) or target web-browsing specifically (IPI-proxy). Research like **Kill-Chain Canaries** (Apr 2026) shows the real question is whether an injected canary progresses through exposure → persistence → relay → **execution**. kinnoo can watch execution directly. `kinnoo redteam -- <any agent cmd>`:
1. plants **canary secrets** (fake API keys, env vars, files) and **injection payloads** in the places agents read: repo files, issue text, tool outputs (via a stub MCP server), web pages, and memory files
2. runs the agent on ordinary tasks
3. detects canaries in **network egress, written files, spawned subprocess args, and memory writes**, not just in chat output
4. outputs a kill-chain report per payload: read? persisted? relayed? executed?

**Reuses:** `src/kinnoo/runtime_monitor.py` (its injected `sitecustomize` network hook `_create_connection_with_monitor` and filesystem event collection are exactly the execution-side sensors), `input_guard.py` (payload families: shell, path traversal, SSRF), `code_sweep.py` (detecting canaries in written files), `sandbox.py` (contain runs), `test_command.py` (scenario orchestration), `init_command.py`'s `mcp-server` template (scaffolding the stub tool server that returns poisoned outputs).

**Why it's distinct:** the 12th's `audit` is static, and the 16th's `ci-guard` is CI-config-specific. This is **dynamic, behavior-level** testing of any agent, filling the gap between response-only canary scanners and full manual red-teaming.

**Honest caveat:** the Python socket hook only sees Python processes. For Node and other agents, network detection needs a local proxy (shared with #1's signing proxy) or OS-level tracing.

**First milestone:** five canary placements × ten payloads, run against `claude -p` and one LangGraph agent, with proxy-based egress detection and a Markdown kill-chain report.

## 4. **Agent engineering lab**: graded, runnable exercises across frameworks

**Pitch:** This repo's notes already frame kinnoo as AI-engineer interview prep and a portfolio piece (`notes/techlead-agent-notes.md`, `notes/ubuntu-apt-lessons-learned.md`), and kinnoo already scaffolds agents in ten framework modes. Turn that into a lab: `kinnoo lab start tool-calling-retries --framework langgraph` scaffolds an exercise (e.g. "add retries with backoff to a flaky tool", "add a human-approval interrupt", "build an MCP server with one paginated resource", "cut token usage 30% without losing accuracy"). `kinnoo lab grade` runs hidden scenario tests plus cost/latency budgets, and a web page tracks progress. The same exercise exists in LangGraph, OpenAI Agents SDK, Pydantic AI, MCP, and no-framework variants, so it doubles as a framework comparison.

**Reuses:** `src/kinnoo/init_command.py` (`SUPPORTED_FRAMEWORKS`: gemini, chatgpt, claude-chat, pydantic-ai, langgraph, openai-agents, mcp-client, mcp-server, openclaw, no-framework) + `templates.py` + `wrapper_templates/` (scaffolding), `test_command.py` + `run_command.py` (grading), `framework_adapters/` (inspect submissions), `server/` auth + tenants + Postgres (accounts and progress), `web/` (exercise catalog and leaderboards).

**Honest positioning:** this is the most *speculative* idea for "agent infra". It's a learning product, not infra, and the evidence for demand here is anecdotal. But it uses almost every part of the repo, works as content marketing for any of the infra ideas, and directly serves your stated goal of interview prep. It's cheap to prototype with 5–10 exercises.

**First milestone:** five exercises × two frameworks (LangGraph, OpenAI Agents SDK), local `start`/`grade` only, no server.

## 5. Refining the 14th's #1 and #5: **don't compete with AgentRegistry; become the trust layer that plugs into it (and into OCI)**

**Context I found in this repo today:** `notes/20260706-terraform-prod-teardown-and-redeploy-AND-retiring-kinnoo.md` records that in July you were weighing **dropping kinnoo and contributing to AgentRegistry** instead, because kinnoo's registry felt like a subset of it. The same note lays out an AWS prod teardown. That bears directly on the 14th's #1 (private MCP/skills registry): AgentRegistry already catalogs agents, MCP servers, skills, and prompts, tracks dependencies, and pushes artifacts to OCI registries. Meanwhile, artifact *storage* across the field is converging on **OCI** (Stacklok Dockyard → GHCR via ORAS + Sigstore, `docker agent share push/pull`, KitOps).

**Pitch:** Stop treating the registry as the product. Keep the parts of kinnoo that AgentRegistry and the OCI tools *don't* emphasize, the **trust pipeline**, and ship them as an add-on that works with any of them:
- **verify-on-pull / verify-on-install:** per-file integrity manifests + Ed25519 detached signatures, checked by the client (kinnoo's original strength)
- **scan-on-publish:** the S3-event → Lambda security check, generalized to registry webhooks or OCI push events, producing a security report attached to the artifact (OCI referrers) or posted back to the registry
- **inspect-before-run:** kinnoo's `inspect` UX, pointed at an AgentRegistry entry or an OCI ref

Deliver these as an AgentRegistry contribution (an extension or plugin, or upstream PRs) plus a standalone CLI that works on raw OCI refs. That captures the July instinct ("contribute instead of compete") without discarding kinnoo's most differentiated code.

**Reuses:** `src/kinnoo/integrity.py`, `checksum.py`, `signing.py` (`create_detached_signature_artifacts` / `verify_detached_signature_artifacts`), `inspect_command.py`, `install_command.py` verification paths, `registry_backend.py` (`RegistryBackend` protocol) + `registry_backends.py` (add an OCI/AgentRegistry-backed implementation), `archive.py` (`ArchiveBackend` protocol), `lambda_handler.py` + `Dockerfile.lambda` + `server/services/security_check.py` (scan-on-publish), `iac/modules/lambda-security-check` + `iac/modules/ecr`.

**Why it's a refinement:** it replaces the 14th's "build a registry" with "be the verification layer for the registries people already use". It also hardens the 14th's #5 (hosted verification) by targeting real distribution channels instead of kinnoo's own `.kno` archives.

**First milestone:** read AgentRegistry's extension points. Prototype `kinnoo verify <oci-ref>`, which pulls a Dockyard- or AgentRegistry-published skill, checks a kinnoo integrity manifest + signature attached as an OCI referrer, and runs `code_sweep`. Then open a design discussion upstream.

### Running synthesis (6 days, 30 ideas)
Today adds a fourth lane to the earlier three (distribution, trust and safety, measurement): **identity and provenance** (#1 Web Bot Auth, #2 Agent Trace). Both ride brand-new standards where tooling lags, and both lean on `signing.py`, which has been underused in earlier ideas. For a *fast, novel* bet, **#1 Web Bot Auth** stands out: standards-backed, low competition for the indie-developer segment, small scope, and most of the crypto already exists.

**Correction to earlier days:** the 14th described the backend as "a real, deployed registry platform" and ranked the registry track as the strongest restart point. Given the July note (considering AgentRegistry instead, and a planned prod teardown), that ranking was wrong. Any registry-shaped idea should now be read as **"complement or contribute to AgentRegistry,"** per today's #5, not "build a competing registry." Ideas that don't overlap AgentRegistry (12th audit/lockfile, 15th share/checkpoint, 16th ci-guard, today's #1–#3) are the safer bets for a standalone kinnoo.
