## 1. **`kinnoo localfit`**: will *my* agent's tools work on *this* local model + runtime + parser + quantization?

**Pitch:** Teams increasingly try running agents on open-weight models (cost, privacy, air-gapped). Tool calling is where it breaks, and usually not because of the model. NVIDIA's NemoClaw docs and an Oct 2026 survey of runtimes point to the **serving layer's tool-call parser and chat template**. vLLM, SGLang, Ollama and llama.cpp ship 136 different parsers between them, coverage differs by model family, a wrong `--tool-call-parser` leaks tool calls as plain text, and quantization below about Q4_K_M visibly hurts reliability. Generic leaderboards (BFCL, Docker's evaluation) can't tell you whether *your* 23 tools with *your* schemas survive. `kinnoo localfit`:
- extracts your agent's actual tool definitions (from the framework code or a running MCP server)
- starts each candidate model × runtime × parser × quant combination, waits for readiness, and runs a scripted set of single- and multi-step tool tasks against it
- reports, per combination: valid tool-call rate, "leaked as text" rate, schema violations, the depth at which multi-step chains fail (practitioners report a wall around the fourth call), and latency
- recommends the working combination and prints the exact launch flags, e.g. `vllm serve … --enable-auto-tool-choice --tool-call-parser hermes`

**Reuses:** `src/kinnoo/supervisor.py` (`start_server`, `wait_until_ready`, `stream_output`, `shutdown_server_with_report`: start and stop each inference server in turn), `health_check.py` (`run_service_health_check`, `_check_http` for OpenAI-compatible `/v1/models` readiness), `framework_adapters/` (`langchain_adapter.apply`, `langgraph_adapter.apply`, `openai_adapter.apply` → extract tool definitions), `analyzer._detect_framework`, `templates.py` (`BaseMCPAgent`, which already connects to an MCP server and lists its tools), `test_command.py` (task suite + assertions), and `size_format.py`.

**Why it matters:** "which local model should I use for tool calling?" is one of the most-asked practical questions, and the answer depends on your tools and your serving stack. A run on your own machine that says "Qwen on vLLM with the `hermes` parser: 97%. The same model on Ollama Q3: 61%, leaks JSON as text" saves days.

**First milestone:** Ollama and vLLM, three model families, tools extracted from an MCP server, 20 generated tasks, and a Markdown matrix with recommended flags.

## 2. **`kinnoo killswitch`**: one command to contain a misbehaving agent, plus drills that prove it works

**Pitch:** Agent incident response became a mainstream topic this month (The Hacker News, CSO Online's "first 24 hours", the Cloud Security Alliance, OWASP's Agentic Top 10 and Non-Human Identities Top 10). The consensus: a kill switch is a *tested set of controls* that must sit **outside the agent's reasoning loop**. It stops running and queued work, revokes credentials (including ones delegated downstream), quarantines tool and MCP access, preserves evidence, and gets drilled regularly. Enterprises get this from ServiceNow or JumpCloud. Individual developers and small teams running Claude Code, Codex, `jobs` (13th #5) or self-hosted agents have nothing. `kinnoo killswitch`:
- **inventory:** knows which credentials each agent can reach (from `vault` grants, `scope` profiles and the inventory, or by scanning configs on demand) and how to revoke each one (provider revocation endpoints for GitHub, AWS, OpenAI, Anthropic, Slack and others)
- **contain:** `kinnoo killswitch <agent|all>` stops agent processes and queued jobs, revokes or rotates the mapped tokens, disables the agent's MCP servers by moving the config entries into quarantine, and blocks egress if a sandbox profile exists
- **preserve:** snapshots logs, transcripts, traces and file changes into a signed evidence bundle *before* cleanup
- **drill:** `kinnoo killswitch drill` does all of the above against throwaway credentials and reports time to contain, which tokens actually stopped working, and anything the agent could still reach

**Reuses:** `src/kinnoo/supervisor.py` (`stop_daemon_pid`, `daemon_pid_is_running`, `clear_daemon_state`), `auth_command.py` (`logout_command`, `_attempt_token_revocation`: kinnoo already revokes its own OAuth tokens and clears local auth state, so this generalizes it to other providers), `uninstall_command.py` (precise config removal patterns → reversible quarantine), `install_trace.py` (`write_violation_event`, `write_uninstall_trace` → the incident log), `code_sweep.py` (`sweep_env_var_exposure`, `sweep_asset_credential_risks` → find credentials when no inventory exists), and `signing.py` + `integrity.py` (a tamper-evident evidence bundle).

**Why it matters:** "can you actually stop it?" is the question every agent-security write-up now ends with, and for anyone outside an enterprise IAM stack the honest answer is "kill the terminal and hope." The drill is the differentiator: it turns a runbook into a measured, repeatable test.

**First milestone:** local scope only. Stop Claude Code and Codex processes and any kinnoo jobs, quarantine MCP entries in their configs, revoke GitHub fine-grained PATs and one cloud API key type, produce an evidence bundle, and run a drill with a time-to-contain report.

## 3. **`kinnoo hookfuzz`**: test and fuzz your agent hooks and deny rules before an agent finds the gap

**Pitch:** Hooks and deny rules (Claude Code `PreToolUse` and `permissions.deny`, and their Codex and Cursor equivalents) are how developers try to enforce "never `rm -rf`," "never read `.env`," "never `git push --force`." They leak in well-documented ways: deny evaluation reportedly checks only the first token of a compound command, and reportedly stops enforcing above 50 subcommands. Hand-written hooks match with `startswith()` or `^`-anchored regexes. Hooks return the wrong JSON and silently allow everything. Agents edit the hook script itself. Agents route around a blocked command with `python -c`, `$(…)`, `env` indirection or another tool, and one developer needed five rounds to stop Claude reading `.env`. Anthropic has said deny rules are a convenience, not an adversarial boundary. Yet nobody *tests* their hooks. `kinnoo hookfuzz`:
- reads your hook config and deny rules, and generates a corpus of **semantically equivalent variants** for each thing you meant to block: chaining (`&&`, `;`, `|`, newline), subshells, quoting and escaping, aliases and `env`, alternate interpreters, alternate tools (Write vs Bash vs MCP), path tricks (`./.env`, symlinks, globbing) and long compound commands
- feeds each variant to the hooks as a synthetic tool-call event, exactly as the agent would send it, and checks that the decision comes back in the correct JSON shape
- reports which variants slip through, plus structural problems: hook scripts writable by the agent, hooks that fail open on error, and rules shadowed by an allow rule
- runs in CI so a hook change can't silently weaken enforcement

**Reuses:** `src/kinnoo/input_guard.py` (`InputGuard` protocol, `RegexInputGuard`, the `SHELL_INJECTION` / `PATH_TRAVERSAL` pattern sets → seed corpus and a second-opinion checker), `sandbox.py` (`_iter_attempted_capabilities`, `evaluate_sandbox_permissions`), and `test_command.py` (declarative cases and assertions → `hooks.test.yaml`). **Dogfood:** `sandbox._iter_attempted_capabilities` is itself a token-matching parser that reads only explicit flags like `--shell` / `-c`, the same class of naive matcher this tool would flag. It makes a good first test subject.

**How it differs from the 16th's `ci-guard` and the 17th's `redteam`:** `ci-guard` lints CI workflows, and `redteam` checks whether *injected content* changes what the agent does. `hookfuzz` checks whether *your guardrail code* does what you think, deterministically and with no model in the loop. Fast and cheap enough for every commit.

**First milestone:** Claude Code `PreToolUse` command hooks plus `permissions.deny`: a variant generator for Bash and the read tools, a synthetic event runner, a pass/fail report, and a GitHub Action.

## 4. **`kinnoo compaction-probe`**: do your agent's rules survive context compaction?

**Pitch:** Long-running agents compact or summarize history when the context fills up, and **compaction drops rules**. A study reported in a blog post ("Lost in Context Compaction", summarized secondhand) found compactors kept only 17% of injected side constraints, and one agent deleted emails without approval in 30 of 100 post-compaction sessions, while task scores stayed fine, so ordinary evals miss it. A NeurIPS 2026 paper studies "instruction survival" through compaction. Anthropic's long-running-harness post says compaction alone isn't sufficient and recommends persistent artifacts. Developers have no way to test *their own* harness and compaction strategy. `kinnoo compaction-probe`:
- takes your agent plus a list of **must-survive constraints** ("never push to main", "ask before deleting", "use the staging DB", "the user's name is …")
- drives the agent through a long scripted session that forces one or more compactions (padding tasks, large tool outputs) and then **probes behaviorally**: it creates an opportunity to violate each constraint and watches what the agent *does* (files touched, commands run, network calls), not what it says
- reports survival rate per constraint and per compaction strategy (built-in auto-compact, custom summarizer, structured notes/artifact files), and flags where re-fetches after compaction reveal lost state
- compares strategies side by side, so you can show that pinning rules in `CLAUDE.md` or a progress file beats leaving them in the conversation

**Reuses:** `src/kinnoo/runtime_monitor.py` (filesystem and network events, `_record_event` → behavioral violation detection), `test_command.py` (`run_test_command` and declarative assertions for "constraint held / violated"), `run_command.py` and `supervisor.stream_output` (drive and capture long sessions), `framework_adapters/` (tool-call capture for LangGraph and OpenAI Agents harnesses), and `install_trace.write_violation_event` (structured violation log). Pairs with the 19th's #3 (each violation becomes a Harbor task) and the 15th's #4 (A/B two compaction strategies).

**Why it matters:** compaction is the least-tested component of every long-running agent and the one most likely to quietly undo safety rules. This is cheap to run, produces a striking demo ("rule survival: 22% → 96% after moving it into a pinned file"), and belongs to the inference-time harness layer that `notes/kinnoo-and-harnesses.md` flags as kinnoo's gap.

**First milestone:** Claude Code headless (`claude -p` with a long scripted session) plus one LangGraph agent with a summarizing memory. Five constraint templates, forced compaction, behavioral probes via the monitor, and a survival report.

## 5. **`kinnoo trace-reqs`**: requirement → task → test → code traceability for spec-driven agent development

**Pitch:** Spec-driven development (GitHub Spec Kit, Kiro, OpenSpec, BMAD, Tessl) is how teams try to keep agents on rails. Its acknowledged weak point is **drift**: once code is written and tests pass, the spec goes stale. Böckeler (Thoughtworks) doubts any tool truly implements "spec as source", and there's little concrete tooling for **requirement-to-test traceability**, such as CI checks that fail when a requirement has no test or a test no longer maps to a live requirement. kinnoo has lived this: the repo itself runs a strict feature → task → test hierarchy (`FEATURES.txt`, `TASKS.txt`, `TESTS.txt`, `EPICS.txt`) enforced by `scripts/validate_project_manifests.py`, with role agents in `.github/*.agent.md` refusing to implement work without linked IDs. `kinnoo trace-reqs` turns that discipline into a tool that **reads the existing spec formats** instead of imposing kinnoo's own:
- parses Spec Kit `spec.md` / `tasks.md`, Kiro `requirements.md` (EARS acceptance criteria) / `tasks.md`, OpenSpec changes, or plain ID-tagged Markdown
- links requirements → tasks → tests (by ID tags in test names or docstrings) → changed code (via the PR diff)
- CI checks: requirement with no test, test with no live requirement, task marked done but its tests missing or failing, and a PR that changes code under a requirement without touching its spec (a drift warning)
- writes a traceability matrix into the PR comment, so the human reviewing an agent's PR sees which requirements it claims to satisfy and the evidence

**Reuses:** `scripts/validate_project_manifests.py` (the ID-linking and validation logic, used daily in this repo), the governance pattern in `.github/techlead.agent.md`, `swe.agent.md` and `test.agent.md`, `src/kinnoo/validator.py` (structured error collection and messages), `diff_command.py` (`_file_change_sets` → map PR changes to requirements), and `test_command.py` (run the linked tests). The `FEATURES`/`TASKS`/`TESTS` files in this repo are a ready-made test fixture.

**Why it matters:** it's the most honest reuse of kinnoo's *process* work, not just its code: years of practice running agents under a feature-task-test contract, packaged as a format-agnostic CI check. It also answers the reviewer's question on every agent PR: "what was this supposed to do, and is that tested?"

**First milestone:** Spec Kit and Kiro parsers, ID-tag linking to pytest and Jest test names, three CI checks (untested requirement, orphan test, unspecced code change) and a PR comment matrix. Dogfood it by running it on this repo's own manifests.

### Where today's ideas fit
All five are **deterministic checks on things developers currently take on faith**: that the local model calls tools correctly (#1), that the agent can actually be stopped (#2), that the guardrails block what they claim to (#3), that rules survive compaction (#4), and that the code matches the spec (#5). That fits the direction from the past few days: kinnoo as the verification layer around other people's agents and formats.

If picking one: **#3 `hookfuzz`**. It's tiny, needs no model calls, has a well-documented bug class to point at, gives a clear "N of 40 variants bypass your hook" result, and is the natural companion to the 18th's `scope`, which generates the rules that `hookfuzz` then tests.
