# kinnoo pivot ideas — 2026-11-14

**Builds on:** [20261112](20261112-ideas.md) (audit, lockfile, policy runner, test harness, describe) and [20261113](20261113-ideas.md) (cross-agent installer, vault, trace, `mcp check`, jobs). Those ideas were all *client-side*. Today's ideas focus on the **server and infra half of this repo** (`server/`, `iac/`, `lambda_handler.py`, `web/`), which the earlier days didn't use at all.

**What the backend already is:** a FastAPI, multi-tenant registry with:
- publish/search/download/agent-detail routes (`server/routes/publish.py`, `search.py`, `download.py`, `agents.py` including a `/security-report` endpoint)
- OIDC login via Kinde (`server/auth/oidc.py`), its own JWT service (`server/auth/token.py`, HMAC-signed), sessions, registration/password-reset tokens (`server/auth/tokens.py`), and auth middleware
- tenant and user stores (`server/storage/tenant_store.py`, `user_store.py`), Postgres metadata (`server/metadata/postgres_manager.py`, Alembic migrations), and S3 or local artifact storage (`server/storage/s3.py`, `local.py`)
- an event-driven **post-publish security pipeline**: an S3 publish event triggers a Lambda (`lambda_handler.py`, `iac/modules/lambda-security-check`) that runs signature and per-file integrity checks (`server/services/security_check.py`)
- production Terraform for AWS (`iac/modules/`: vpc, alb, ecs-fargate, ecr, rds-postgres, s3-registry, secrets, iam, cloudflare, plus dev/prod environments) and Dockerfiles
- a Next.js web front end (`web/`) that proxies to the backend (`web/lib/backend-proxy.ts`, `registry-client.ts`).

That's a real, deployed registry platform. The pivot question is what it should *hold* and *do* once it stops requiring the kinnoo format.

**Field signals today:**
- The **official MCP Registry won't host private servers**, says its codebase isn't built for self-hosting, and explicitly invites organizations to build *compatible sub-registries* on its open OpenAPI spec and `server.json` format. Vendors are filling this (Azure API Center, JFrog, ServiceNow, Portkey/TrueFoundry), but there's no obvious lightweight open-source option.
- **MCP authorization is hard to implement.** The 2026-07-28 spec ranks pre-registration > Client ID Metadata Documents (CIMD) > DCR (now deprecated). Most OAuth providers don't support the MCP-required features yet. CIMD fetching is an SSRF risk, and one preprint reports DCR flaws in ~97% of the OAuth-enabled remote MCP servers it tested.
- **Human-in-the-loop** is shifting from "modal prompt" to *durable, async approval* (Slack/email/web, audited). Framework primitives exist (LangGraph, OpenAI Agents SDK), and small OSS projects are appearing (awaithumans, HumanLayer). Reviewer fatigue is the known failure mode: one report says Claude Code users approve ~93% of prompts.
- Self-hosted agent **sandboxes** are crowded (E2B infra, microsandbox, beta9, Temps) and want microVMs/bare metal. I considered and **rejected** a Fargate sandbox idea for that reason.

---

## 1. Turn the registry into an open-source, self-hostable **private MCP sub-registry** (+ skills/plugins)

**Pitch:** Implement the official MCP Registry OpenAPI spec and `server.json` format on kinnoo's existing backend, so any MCP client that speaks the registry API can point at `registry.yourcompany.com`. Add what enterprises actually want on top: per-tenant **curation** (an allowlist that mirrors approved upstream servers), private entries for internal servers, approval workflow for new entries, and a security report per version. Index Agent Skills and Agent Plugins 1.0 packages the same way. Artifacts can stay where they are (npm/PyPI/OCI). The registry stores metadata and pins, and optionally mirrors artifacts.

**Reuses:** almost the entire server. `server/routes/publish.py`, `search.py`, `agents.py`, `download.py` (map onto registry API endpoints), `server/metadata/postgres_manager.py` + migrations, `server/storage/s3.py` (optional mirroring), `tenant_store.py` + `server/auth/*` (multi-tenancy and SSO are the paid-tier features vendors charge for), `web/` (catalog UI), `iac/` (one-command AWS deploy). The 13th's cross-agent installer (#1) becomes this registry's natural client.

**Why it's the strongest server-side idea:** the MCP project explicitly asked for compatible sub-registries, the main options are proprietary platforms, and kinnoo already has ~80% of a multi-tenant registry with SSO, storage, search, and Terraform. It's the original "registry" thesis pointed at a standard format.

**First milestone:** read-only registry API (`GET /v0/servers`, `/v0/servers/{id}`) backed by Postgres; a `kinnoo-registry sync --from official --allow list.txt` mirror job; a web catalog page per server.

## 2. A drop-in **OAuth 2.1 authorization server for MCP servers** (CIMD-first)

**Pitch:** Most teams building a remote MCP server get stuck on auth. Their IdP (Okta, Auth0, Cognito, Kinde) doesn't support CIMD or resource indicators the way MCP requires, and DCR is deprecated and easy to get wrong. kinnoo ships a small authorization server that sits **in front of an existing IdP**. It delegates user login to OIDC, then handles the MCP-specific parts itself: protected-resource metadata, authorization-server metadata with `client_id_metadata_document_supported`, safe CIMD fetching (HTTPS-only, block private/loopback IPs, exact `client_id` match), PKCE, audience-bound tokens, consent screens, and per-tenant revocation.

**Reuses:** `server/auth/oidc.py` (upstream OIDC relying-party flow is already done, including the Kinde provider), `server/auth/token.py` (token issuance/validation), `session.py`, `middleware.py`, `tenant_store.py` / `user_store.py`, `server/routes/auth.py` + `web_auth.py` (login/consent UI), `src/kinnoo/input_guard.py` (its SSRF detection is directly relevant to CIMD fetching).

**Honest gap:** `token.py` signs with a shared HMAC secret. MCP resource servers need to validate tokens independently, so this needs asymmetric keys and a JWKS endpoint (RS256/ES256), plus key rotation, before it's usable.

**First milestone:** metadata endpoints + CIMD client registration + an authorization-code/PKCE flow delegating to one upstream OIDC provider + JWKS. Ship a conformance test against the MCP Inspector and Claude/Cursor clients.

## 3. **Remote MCP deploy**: one command from a stdio MCP server to an authenticated HTTPS endpoint on your AWS

**Pitch:** Lots of useful MCP servers are stdio-only, so they only work on one laptop. `kinnoo deploy mcp ./my-server` (or `npx some-mcp-server`) builds a container that bridges stdio to Streamable HTTP, pushes it to ECR, and runs it on ECS Fargate behind the ALB and Cloudflare. Auth comes from idea #2 and secrets from AWS Secrets Manager. The result is a team-shared remote MCP endpoint with SSO, logs, and health checks, in your own account rather than a third-party host.

**Reuses:** `iac/modules/ecr`, `ecs-fargate`, `alb`, `cloudflare`, `secrets`, `iam`, `vpc` (this is exactly the stack those modules already provision for the registry), `Dockerfile`, `src/kinnoo/health_check.py` + `supervisor.py` (readiness/liveness for the bridged process), `src/kinnoo/analyzer.py` (detect how to start the server from a repo), `server/auth/*` / idea #2 for the OAuth front.

**Why it matters:** remote MCP + OAuth is where the ecosystem is heading, but converting and hosting servers is still DIY. Hosted MCP platforms exist, but "self-host on my AWS with Terraform I can read" is a real buyer preference, especially for servers that touch internal systems.

**First milestone:** stdio→Streamable HTTP bridge container + a Terraform module (`iac/modules/mcp-service`) parameterized by image/env/secrets + `kinnoo deploy mcp` wiring it together for one server.

## 4. **Async approval service**: durable human-in-the-loop for agent actions

**Pitch:** A small, self-hosted API where agents (or the 12th's policy runner and 13th's `jobs`) `POST /approvals` with an action, context, and risk level, then wait or poll. Humans approve or reject from a web inbox, an email link, or (later) Slack. Every decision is stored with who, when, and why. Policies decide what *needs* approval, so only irreversible or high-risk actions are gated, which avoids rubber-stamping. A Python/TS SDK provides `@requires_approval` plus adapters for LangGraph interrupts and OpenAI Agents SDK tool approvals. An MCP server exposes `request_approval` as a tool.

**Reuses:** `server/services/email_service.py` + `email_console.py` (approval-link emails), `server/auth/tokens.py` (the signed, expiring registration/reset tokens are exactly the pattern for one-click approve/reject links), `server/auth/*` + `tenant_store.py` (who may approve what, per team), Postgres metadata + migrations (durable pending state and audit log), `web/` (approval inbox), `src/kinnoo/sandbox.py` permission model (as the policy language for "what needs approval").

**Why it matters:** durable approvals plus an audit trail is what compliance teams ask for before letting agents act. Framework primitives handle the *pause*, but not routing, identity, policy, or audit. The OSS options are very young.

**First milestone:** `POST/GET /approvals`, email approve/reject links with signed expiring tokens, a web inbox, a Python SDK decorator, and a LangGraph `interrupt` adapter.

## 5. Refining the 12th's #1: a **hosted verification pipeline** (scan on publish, attest, badge)

**Pitch:** The 12th proposed `kinnoo audit` as a local CLI. The server already has the hosted half: **S3 publish event → Lambda → security report → API endpoint**. Generalize it so any skill, MCP server, or plugin repo can be submitted (via GitHub App/webhook, or by being added to the registry in idea #1) and get: the full audit ruleset run in an isolated Lambda, a signed **attestation** (in-toto/SLSA-style statement over content hashes and findings), a public report page, and a README badge. Registries and the 12th's lockfile can then *require* a valid attestation for a given hash.

**Reuses:** `lambda_handler.py` + `Dockerfile.lambda` + `iac/modules/lambda-security-check` (event-driven isolated scanning is already deployed), `server/services/security_check.py` and the `/security-report` route in `server/routes/agents.py`, `src/kinnoo/code_sweep.py`, `input_guard.py`, `integrity.py`, `checksum.py`, `signing.py` (sign attestations), `web/` (report pages).

**Why it's a refinement, not a repeat:** the 12th's #1 was a local scanner. This is the *publisher-facing, hosted, attested* counterpart, which gives the scanner distribution (badges spread it) and makes the results verifiable by third parties. It matters because static scanning alone can be evaded, so signed, hash-bound results plus re-scans on every new version beat one-off scans.

**First milestone:** a GitHub webhook → Lambda scan of a skill/MCP repo at a commit SHA → a signed JSON attestation stored in S3 → a public report page + an SVG badge endpoint.

---

### Synthesis after three days
The client-side ideas (12th, 13th) and today's server-side ideas fit one product: **an open-source, self-hostable trust and control plane for agent tooling.** Today's #1 (private MCP/skills registry) is the hub. #2 and #3 make remote MCP servers deployable and securely authenticated. #4 adds human oversight. #5 adds verifiable trust. Of everything so far, **#1 today + the 13th's cross-agent installer** reuse the most existing code on both sides of the repo and ride an explicit invitation from the MCP project, so that pair looks like the best restart point.
