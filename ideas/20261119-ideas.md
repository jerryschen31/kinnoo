# kinnoo pivot ideas — 2026-11-19

**Builds on:** [12th](20261112-ideas.md), [13th](20261113-ideas.md), [14th](20261114-ideas.md), [15th](20261115-ideas.md), [16th](20261116-ideas.md), [17th](20261117-ideas.md), [18th](20261118-ideas.md). That's 35 ideas so far. Today's #1 refines the 13th's #4 (`mcp check`), and today's #3 refines the 12th's #4 test harness and the 15th's #4 A/B harness. #2, #4 and #5 are new.

**Considered and dropped today:**
- *A parallel-agent worktree manager on its own* (create worktrees, launch agents, merge). Conductor, Crystal, claude-squad, vibe-kanban and Claude Code's own worktree support cover it. Only the *runtime* half (ports, databases, env) is underserved, and that half is #2.
- *An "A2A gateway" with delegation budgets.* The gap is real (A2A defines no way to cap spend when one agent delegates work to another), but gateway vendors (Gravitee, agentgateway) already pitch this, and kinnoo has nothing to start it from.

## 1. Refining the 13th's #4: **`kinnoo mcp compat`**: dual-era conformance plus a breaking-change classifier for tool contracts

**Pitch:** The 2026-07-28 MCP release is the largest revision since launch. It removes the `initialize` handshake and changes transport, authorization and tool-schema handling, and the spec now speaks of "legacy", "modern" and "dual-era" implementations. Meanwhile, only the protocol revision and the package version have an agreed versioning scheme. **Tool schemas and descriptions have none**, and renaming a tool, narrowing an enum or rewording a description silently changes agent behavior. Server authors need two answers in CI:
- **Which eras do I support?** Run the server against a legacy client and a modern client, and report a matrix of what passes, what degrades and what breaks (handshake, transport, auth discovery, tool listing, error shapes).
- **Is this release breaking?** Diff `tools/list` against the last released version and classify each change: *breaking* (tool removed or renamed, new required field, enum narrowed, type or units changed), *behavioral* (description or annotation changed, which affects how models pick the tool) or *additive*. Then fail the build if the version bump is too small, e.g. a breaking change shipped as a minor release.

**How it differs from the 13th's #4 and the 12th's #2:** `mcp check` scored one version's quality, and the lockfile detects *consumer-side* rug pulls by hash. This is the *author-side* counterpart: semver discipline for tool contracts, plus the spec migration everyone has to make this year.

**Reuses:** `src/kinnoo/supervisor.py` (`start_server`, `wait_until_ready`, `stream_output`, `shutdown_server_with_report` to drive the server under test), `health_check.py` (`run_service_health_check`, `_check_http`, `_check_process`), `diff_command.py` (`_manifest_change_lines` → per-tool change lines), `validator.py` (`_collect_mcp_server_permissions_errors` and the structured-error style), `test_command.py` (`run_test_command` for the era matrix), and `pack_command._bump_core_semver` (suggested version bump). Dogfood: kinnoo's own MCP server template in `templates.py` still hard-codes `"protocolVersion": "2024-11-05"` in its `initialize` handler, so it is the first legacy server to migrate.

**First milestone:** stdio servers. A `tools/list` snapshot plus a diff classifier with `--fail-on breaking`, a GitHub Action, and a legacy-versus-modern handshake check against the official SDK clients.

## 2. **`kinnoo lanes`**: per-worktree *runtime* isolation for parallel coding agents

**Pitch:** Running several agents in parallel on git worktrees is now standard practice, and every guide hits the same wall: **worktrees isolate files, not runtime**. Agents collide on ports, share a dev database (so one agent's migration breaks another's tests), clobber each other's `.env`, and leave orphaned dev servers behind. Advice exists (port offsets, Neon branch per worktree, preview environments), but it is spread across blog posts and per-project scripts. `kinnoo lanes` is the missing piece:
- `kinnoo lane up` in any worktree reads the project's services (inferred from `docker-compose`, `package.json` scripts, `Procfile`, or a short `.kinnoo/lanes.yaml`) and allocates a **lane**: a unique port block, a per-lane database (Postgres schema or `CREATE DATABASE … TEMPLATE`, SQLite copy, or a Neon/PlanetScale branch via their CLIs), and a generated `.env.lane` that overrides only what has to differ
- starts the services under supervision with readiness checks, so the agent gets "app ready at :4123", not a race
- `kinnoo lane ls` / `down` / `gc` shows and reaps lanes, including orphaned servers from crashed agent sessions
- exposes an MCP tool (`lane_info`) or a hook, so the agent *knows* its own URLs and database instead of guessing `localhost:3000`

**Reuses:** `src/kinnoo/supervisor.py` (`start_server`, `wait_until_ready`, `write_daemon_state` / `build_daemon_state_payload`, `daemon_pid_is_running`, `stop_daemon_pid`, `shutdown_server_with_report`: this is already a per-directory daemon manager with state files), `health_check.py` (`run_service_health_check`, `classify_daemon_lifecycle_state` for "running / stale / orphaned"), `validator._collect_services_shape_errors` (kinnoo's manifest already has a multi-service shape to borrow for `lanes.yaml`), `analyzer._detect_runtime` and `_detect_runtime_port_hint` (infer services and default ports), `config.py` (project config discovery). It pairs with the 15th's #3 checkpoint and the 18th's #1 scope, which work per lane.

**Why it matters:** parallel agents multiply throughput only if their environments don't interfere. Worktree tooling is crowded, but runtime isolation is still DIY, and it's exactly where kinnoo's supervisor code already lives.

**First milestone:** Node and Python web apps with Postgres. A port-block allocator, a per-lane Postgres database from a template, `.env.lane`, `lane up/ls/down/gc`, and a Claude Code `SessionStart` hook that prints the lane's URLs into context.

## 3. Refining the 12th's #4 and the 15th's #4: **turn your agent's real failures into Harbor tasks**: a private eval set in the *standard* format

**Pitch:** The 12th proposed a kinnoo-native test harness. That's the same mistake as the original pivot: inventing a format. The field has since converged. **Harbor**, the Terminal-Bench team's framework, defines a task as a directory with `task.toml`, an environment, and a verifier that writes its own reward. Harbor Hub hosts the datasets, and runs go to local Docker, Vercel Sandbox or other cloud backends. What teams lack is a fast way to turn *their own* incidents into such tasks. `kinnoo harbor`:
- `kinnoo harbor capture <session or PR>` takes a real failure (an agent session transcript, a reverted agent PR, a failing CI run) and drafts a task: the starting repo snapshot as the environment, the user's request as the instruction, and a verifier built from the fix's tests or the reviewer's check
- infers the environment `Dockerfile` from the repo instead of making you write it
- validates the task: the verifier fails on the starting snapshot and passes on the known fix, so the task is neither trivial nor impossible
- then **hands off to Harbor itself** for running, so kinnoo owns authoring and validation, not execution

**Reuses:** `src/kinnoo/analyzer.py` (`_detect_runtime`, `_detect_dependencies`, `_infer_requirements` → environment Dockerfile), `test_command.py` (declarative assertions, `validate_kinnoo_tests_document` → verifier scripts that write the reward file), `check_command.check_target` (clone and preflight a repo snapshot), `import_command.clone_github_repo`, `pack_command.py` + `integrity.py` (content-addressed task snapshots), `code_sweep.sweep_memory_snapshot_credential_risks` (scrub secrets from captured transcripts and snapshots before they become shared tasks). `notes/kinnoo-and-harnesses.md` already rates kinnoo's evaluation harness as only "Medium". This raises that rating by adopting the standard rather than competing with it.

**Why it matters:** public benchmarks don't reflect your repo or your failure modes, and the 15th's A/B idea needs a task suite to be meaningful. "Every agent incident becomes a regression task" is the eval equivalent of "every bug gets a test."

**First milestone:** from a GitHub PR that fixed an agent-written bug, produce a Harbor task directory (the parent commit as the environment, the fix's tests as the verifier). Validate it fails before the fix and passes after, then run it with `harbor run` locally.

## 4. **`kinnoo cachecheck`**: find what's breaking your agent's prompt cache

**Pitch:** Prompt caching cuts agent API costs by roughly 45–80% (per a Jan 2026 multi-provider evaluation), but it fails silently. A timestamp in the system prompt, `json.dumps` without `sort_keys`, a tool list built from a `set`, framework middleware injecting a trace ID, or rewriting earlier turns all invalidate the prefix, and the first symptom is a bill that "tripled overnight." `kinnoo cachecheck` finds the cause:
- **static:** scan agent code for volatile values flowing into system prompts or tool definitions (`datetime.now()`, `uuid4()`, `time.time()`, unsorted dict/set serialization, environment-dependent tool ordering), with framework-aware rules for LangChain, LangGraph, the OpenAI Agents SDK and raw Anthropic/OpenAI clients
- **dynamic:** `kinnoo cachecheck -- <agent command>` records the *rendered* requests across turns and across two runs, reports the **first byte offset where the prefix diverges** and which section it falls in (system, tools, history), and computes the cache hit rate from the usage fields providers return
- suggests fixes: move volatile content after the cache breakpoint, sort keys, freeze tool order, and cache only the system prompt when tool results are mostly dynamic

**Reuses:** `src/kinnoo/analyzer.py`, which already walks Python ASTs (`_name_from_ast_node`, `ast.walk` over project sources) and detects frameworks (`_detect_framework`); `framework_adapters/` (`langchain_adapter`, `langgraph_adapter`, `openai_adapter`, `read_text_files`) for framework-specific rules; `runtime_monitor.py`'s sitecustomize injection (`_build_sitecustomize_source`), which is already a mechanism for hooking a child Python process without code changes and could wrap the HTTP client the same way it wraps `socket.create_connection`; `run_command.py` (process launch); and `size_format.py` (token/byte reporting).

**Why it matters:** this saves money directly and measurably, and the result is easy to demo ("your cache hit rate went from 3% to 91%"). It's also squarely inside the "inference-time harness" layer that `notes/kinnoo-and-harnesses.md` says kinnoo doesn't cover yet. Provider dashboards show hit rate but not *why* the cache missed.

**First milestone:** the dynamic mode for Python agents using the Anthropic or OpenAI SDKs. Prefix diff across turns, first-divergence report and hit rate, plus five static rules (timestamp, uuid, unsorted `json.dumps`, set-ordered tools, f-string with request ID in the system prompt).

## 5. **x402 spend-policy proxy and go-live rehearsal** for agents that pay for tools (speculative)

**Pitch:** Agent payments over HTTP 402 (x402) went from demo to real in 2026: Coinbase, Stripe and Cloudflare support, Base docs, AWS AgentCore Payments. The consistent complaint is **spend control**. Built-in limits are mostly per session. Practitioners ask for per-endpoint caps, task-level budgets, duplicate-payment detection and recipient allowlists, enforced *outside the prompt*, plus a way to rehearse before spending real money. Nobody has a standard test harness. `kinnoo pay` is:
- a local forward proxy that intercepts `402 Payment Required` challenges and applies a declarative policy (per-endpoint, per-task and per-day caps; recipient and network allowlists; duplicate detection; "ask a human above $X"), then signs or forwards the payment only if the policy allows it
- `kinnoo pay rehearse -- <agent command>`: runs the agent against a mock facilitator or testnet and produces a report of what it *would* have paid, to whom and why, before mainnet
- an append-only payment log for reconciliation

**Reuses:** `src/kinnoo/runtime_monitor.py` (network-event capture and `resolve_violation_enforcement` for allow/deny decisions), `sandbox.evaluate_sandbox_permissions` (the policy-evaluation shape), `input_guard.py` (`InputGuard` protocol → a pluggable `PaymentGuard`), `signing.py` (Ed25519 for signing the payment log entries), `install_trace.py` (append-only JSONL), and, for "ask a human", the 14th's #4 async approval service on `server/`.

**Honest positioning:** this is the weakest fit with existing code, and the space is moving fast. PolicyLayer, AgentPay MCP and the payment providers themselves are adding controls. It's here because spend governance for paying agents is a clearly emerging gap, and the policy-proxy-plus-rehearsal shape matches kinnoo's "enforce outside the agent" lane. Wait a quarter before building it.

**First milestone:** an HTTP proxy that parses x402 challenges, a YAML policy with per-endpoint and per-task caps, and rehearsal mode against a mock facilitator, with a Markdown spend report.

### Where today's ideas fit
Today adds two cheap, high-utility developer tools (#2 `lanes`, #4 `cachecheck`) and two "adopt the standard" refinements (#1 MCP compat, #3 Harbor). Both refinements follow the lesson from the original pivot: **kinnoo should author, verify and enforce against other people's formats, never define its own.** If picking one to build this week: **#4 `cachecheck`**. It has the clearest ROI, it's small, it reuses the analyzer's AST code and the sitecustomize hook, and nobody would mistake it for the old package manager.
